# 构建加速、缓存加速、OpenWrt 配置优化 —— 本轮落实与待定项

> 2026-11-24 整理。每一项都标明"已落实 / 待定夺 / 不建议"，并附依据。
> 依据里引用的行号是本次整理时仓库 `main@5ed81c3` 的行号；上游源码引用是当日快照。
> 目标内核：四个设备（NN6000 / R68S / NSY-G68-PLUS / SystemReady）全是 Linux 6.12
> （LiBwrt 25.12-nss 的 `target/linux/qualcommax/Makefile:11` 写 `KERNEL_PATCHVER:=6.12`，
> ImmortalWrt openwrt-25.12 / master 的 rockchip、armsr 同样是 6.12）。

## 0. 先说结论：时间花在哪

三次同提交（`5ed81c3`）的真实定时构建（GitHub Jobs API 的 `started_at/completed_at`）：

| 步骤 | NN6000 | NSY-G68-PLUS | R68S |
|---|---:|---:|---:|
| 初始化环境（apt 等） | 384 s (5%) | 99 s (1%) | 7191 s（异常，常态约 310 s） |
| 拉源码 + feeds + DIY2 | 111 s | 145 s | 77 s |
| 恢复缓存 | 10 s | 23 s | 7 s |
| `make download` | 161 s | 104 s | 97 s |
| **编译** | **6527 s (90%)** | **6656 s (94%)** | 6764 s |
| 清理 + 发布 | 36 s | 8 s | 41 s |
| 合计 | 7255 s | 7055 s | 14219 s |

也就是说：**除了编译，其他所有步骤加起来不到 10%**。想真正省时间只有两条路：
让编译少做事（缓存命中、关掉不必要的 debug 产物），或者换更快的机器（8 核 runner，公开仓库要付费）。
本轮落实的都是"零风险、不改固件功能"的项；真正有肉的那些（下面第三节）需要你拍板。

## 1. GitHub Actions 构建加速

### 1.1 已落实

| # | 改动 | 文件 | 为什么安全 | 收益 |
|---|---|---|---|---|
| B1 | `actions/checkout` 的 `fetch-depth: 0` → `1` | 五个 `build-openwrt-*.yml` | 全仓库只有 `git rev-parse HEAD`、`git apply`（作用于工作树）这两类 git 操作，没有任何依赖历史的命令（`git grep` 已核对） | 每次构建少拉全部历史；checkout 本来只占 2-6 s，收益是秒级，主要是减少网络抖动 |
| B2 | 发布前不再 `ls -A \| xargs rm -rf` 删整个构建树 | NN6000 / R68S / SystemReady 的 "Clear server space" 步骤 | 产物已拷到 `output/`，runner VM 任务结束即销毁，删树是纯浪费 I/O；NSY 流本来就没有这一步 | 该步骤 29-30 s，历史上最慢 73 s，去掉后省掉其中大部分 |
| B3 | DIY2 不再从 `raw.githubusercontent.com` 拉本仓库自己的 `config/*.conf`（和 R68S 的 `balance_irq`），改为 `install -m 0644` 从 `$GITHUB_WORKSPACE` 复制 | `NN6000/diy-part2.sh`、`NSY-G68-PLUS/diy-part2.sh`、`R68S/diy-part2.sh` | 只在 `GITHUB_REPOSITORY == happyplum/action-openwrt && GITHUB_REF == refs/heads/main` 时启用，fork 和其他分支保持旧逻辑；已逐字节比对本地与远端 main 一致、文件权限 0644 一致 | 每个 job 少 4-5 次串行 HTTPS 请求，并且**以后改 `config/` 下的文件会随本次提交立即生效**，不用先等它推到 main |

### 1.2 待定夺（有收益，但要你拍板）

| # | 改法 | 收益 | 风险 / 代价 | 建议 |
|---|---|---|---|---|
| B4 | **关掉 `CONFIG_KERNEL_DEBUG_INFO`**（NN6000、SystemReady 开着；R68S/NSY 已关） | 内核和所有 kmod 不再生成 DWARF 调试信息，编译/链接 I/O 减少，`build_dir` 体积明显变小 | 失去在设备上用 `gdb`/`crash` 分析内核的能力；BTF 依赖另有条件（`KERNEL_DEBUG_KERNEL` 是隐藏符号，不要单独改） | 自用固件、不调内核的话建议关；要留就维持 |
| B5 | **关掉 `CONFIG_TARGET_ROOTFS_INITRAMFS`** | 少打一份 initramfs 镜像（cpio + 内核重链） | 已核实：NN6000 的 factory/sysupgrade、Rockchip 的 `sysupgrade.img.gz`、armsr 的 `rootfs.tar.gz` 的 Makefile recipe 都不依赖 initramfs 产物；关掉只失去"救援/直接启动"的 initramfs 文件 | 发布里不传 initramfs 的话可以关 |
| B6 | `KERNEL_DEBUG_FS` | 编译差异小 | NN6000/NSY/SystemReady 开着，`MAC80211_DEBUGFS` 会 `select` 它，硬关会丢 debugfs 调试接口 | **不建议动** |
| B7 | 固定 apt 依赖列表，去掉对 `ophub.org/ubuntu2404-make-openwrt-depends` 的两次 `curl` | 删重复安装、少 1-2 次外部请求；去掉真没用的包才可能省分钟级 | 固定包名等价集合收益小；裁剪包有破坏 host 依赖的风险。R68S 那次 init 7191 s 的异常目前定位不到具体是 apt/NTP/purge 哪一步（匿名日志 403） | 先在 init 里给 update/purge/install/NTP 分开打点，再决定 |
| B8 | 去掉 LVM 合并磁盘 | LVM 创建本身 ≤1 s，省不出什么；可能省的是上游腾盘 | 容量预算：NN6000 峰值约 25-50 GiB、R68S 25-55 GiB（dl 月种子占盘）、其他 20-45 GiB，去掉合并后容易 ENOSPC | **不建议动** |
| B9 | `make download -j8` → `-j$(nproc)` | 公开 runner 是 4 核，这是 8→4 不是加速 | 下载并发减少可能更慢 | **不建议动** |
| B10 | `-j$(nproc+1)` vs `-j$(nproc)` | 可能有分钟级差异，方向不确定 | 链接阶段抢内存，ccache 热了之后最优 `-j` 可能不同 | 要测就同配置 A/B，不要凭感觉改 |
| B11 | 去掉 `V=s` | 减少日志写盘 | 失去 per-target 计时和失败时的完整诊断；compile-openwrt.sh 已用 awk 压缩输出 | **不建议动** |
| B12 | cron 整点错峰（`0 0 / 0 20 / 0 16` → 如 `17 0 / 23 20 / 31 16`） | 降低整点拥堵概率 | 构建时刻变化会改变浮动上游快照；收益不确定 | 可做可不做 |
| B13 | 8 核 larger runner | 编译近两小时，理论上可并行部分能显著缩短 | 公开仓库也要按分钟计费，需要组织计划里配置 | 看预算 |
| B14 | `ubuntu-24.04-arm` runner | 公开免费，但 OpenWrt 是 x64 host 交叉编译 aarch64，换 ARM host 不省工具链编译，还要验证 `gcc-multilib`、第三方 action、loop 挂载 | 中高风险 | **不建议** |
| B15 | 用 `containers:` 跳过 apt | 上限是省掉整段 init | job container 默认 `sh`，要重做 sudo/systemctl/LVM/XFS/`/builder`/`/opt`/缓存路径；Ophub 的 composite 还要 loop 挂载 | **不建议**先碰 |
| B16 | `pin-golang.sh` 前先 `git cat-file -e` 看对象在不在 | 本地命中省一次 fetch；没命中零收益 | 现有缓存不存 git 对象，shallow feeds 多半没有 | 可做可不做 |
| B17 | DIY2 里重复的 `./scripts/feeds update -a`（NN6000/R68S 开头多跑一次） | 省几十秒 | 去掉后从"读两次浮动分支"变成"一次快照"，feeds 结果会变 | 需先固定 feeds 提交再谈 |
| B18 | `find dl -type f -size -1024c -delete` | 这行会无差别删小于 1 KB 的文件，合法的小文件也会被删 | 去掉后要确认 `make download` 的 hash 校验路径覆盖所有 recipe | 先只记录命中不改行为 |

### 1.3 不建议（已验证无效或有副作用）

- `CONFIG_KERNEL_BUILD_USER`：四份 config 已是空串，改它不提速，只改 `uname -a` 字符串。
- `CONFIG_TARGET_OPTIONS` / `CONFIG_USE_LTO`：会改生成代码或编译参数，不是提速项。
- 按 `*debug*` 字符串批量关包：`libudebug` 四台都选，`MAC80211_DEBUGFS` 是功能项，不是多余符号。
- `CONFIG_TARGET_IMAGES_GZIP`：Rockchip 的 `sysupgrade.img.gz` 由 recipe 自带 gzip，不靠这个开关；NN6000 上关它可能改 ext4 factory 产物格式。
- `upgrade-rust.sh`：只是把 feed 里 Rust 1.96.0 的配方换成 1.96.1 修 LLVM 下载，不删。

## 2. GitHub Actions 缓存加速

### 2.1 已落实

| # | 改动 | 文件 | 机制 | 收益 |
|---|---|---|---|---|
| C1 | ccache 缓存 key 从 `ccache-v2-{scope}-{fingerprint}` 改为 `ccache-v3-{scope}-{UTC ISO 周}`；`restore-keys` 先 `v3-` 再 `v2-` | `.github/actions/openwrt-cache/action.yml` | 原来的 key 含源码 rev + feeds 列表 + 设备树 + `.config` 哈希，几乎每次都 miss 精确 key，然后 post-job 又把 200-400 MB 归档再传一遍。GitHub 缓存不可变（同 key 不覆盖），`restore-keys` 多条命中时取**最新创建**的（官方文档 cache-key-matching 原文 "returns the most recently created cache"）。改成按周后：同一周内精确命中、不再重复上传；换周时回退到上一周种子再建新 key。ccache 自己按编译器内容（`CCACHE_COMPILERCHECK=content`）和每个对象的编译参数判断命中，换 GitHub key 不放宽正确性 | 每周每设备最多上传一次而不是每天；下载量不变（精确命中也要下载解包） |
| C2 | 新增 "Report compiler cache match" 步骤，把 `cache-hit` 打成 exact / fallback / miss | 同上 | 方便你在 Actions 日志里直接看命中率 | 可观测性 |

### 2.2 待定夺

| # | 改法 | 收益 | 风险 | 建议 |
|---|---|---|---|---|
| C3 | 把 `dl`（源码包）月度缓存扩到 NN6000 / SystemReady（目前只有 R68S 开） | `make download` 三台分别 161 / 104 / 97 s；dl 目录 R68S 样本 1.92 GB | 每月一次上传 2 GB 级归档，和 ccache 抢 10 GB 仓库配额；月内新增源码不会写回；NN6000/SystemReady 的 clean 步骤和测试要同步保留 `dl` | NN6000 可做下一个试点，先看它一个月的 download 耗时 |
| C4 | `HiGarfield/cachewrtbuild` 工具链缓存扩到另外三台（目前只有 NSY，归档 406 MB，恢复 8 s） | 命中时跳过 host tools 和交叉 GCC 的编译 | 三台都是 branch 跟踪不固定 commit，`mixkey` 没有 revision 维度；宿主/配置/路径错配会复用旧可执行物 | 先给三台固定 `REPO_COMMIT`，再试 `skip: false` 冷/暖对照 |
| C5 | 编译失败也保存 ccache（`actions/cache/restore` + 编译后 `actions/cache/save`） | 晚期失败（单包问题）时保留已编出的对象 | 早期失败不值得传；同周首次失败会"冻住"半暖种子 | 先观察 C1 几周再决定 |
| C6 | `CCACHE_MAXSIZE=2G` 调大 | 暖缓存对象数超过 2G 时少淘汰 | 实际归档 NN6000 285 MB、NSY 425 MB、R68S 228 MB，远没到 2G | **暂不动**，看 `ccache --show-stats` 里的 evicted 数再说 |
| C7 | 缓存保留期/配额调大（2025-11 起仓库设置里可付费调到 10 TB、公开仓库最长 90 天） | 避免按周滚动时旧种子被驱逐 | 要钱 | 默认 7 天未访问淘汰、10 GB 对本仓库够用 |

### 2.3 不建议

- 开 `CCACHE_SLOPPINESS`、`CCACHE_NOHASHDIR`：放宽校验换命中，可能带错调试路径。OpenWrt `rules.mk` 已设 `CCACHE_BASEDIR`，不用再加。
- 把 `dl` 和 `.ccache` 合并成一条缓存：生命周期和版本会绑死，单独命中也要整包拉。
- 缓存命中后跳过 `make download`：OpenWrt 的下载 rule 以文件存在为目标，不重新校验，不能把归档当可信输入。

## 3. OpenWrt 运行时配置（sysctl 等）

### 3.1 核对方法

把 `config/0-base.conf`、`0-v4.conf`、`0-v6.conf`、`1-netfilter.conf` 的每一行 key，
对照 **Linux v6.12 源码**（`net/core/sysctl_net_core.c` 的 `net_core_table[]`、
`net/ipv4/sysctl_net_ipv4.c` 的 `ipv4_net_table[]`/`tcp_table[]`、`net/ipv4/devinet.c` 的
`DEVINET_SYSCTL_RW_ENTRY` 宏、`net/core/neighbour.c` 的 `neigh_parms` 表、
`net/netfilter/nf_conntrack_standalone.c` 的 `nf_ct_sysctl_table[]`/`nf_ct_netfilter_table[]`、
`fs/file_table.c`、`net/bridge/br_netfilter_hooks.c`）逐个确认 procname 是否存在，
再 grep 两套源的全部内核补丁（ImmortalWrt 25.12 共 878 个、LiBwrt 25.12-nss 共 624 个）看是否有 patch 另行添加。

**一个教训**：四台设备共用同一份 `config/*.conf`，但源码树不同（NN6000 用 LiBwrt，其余用 ImmortalWrt）。
同一个 key 可能在一边是补丁加的、另一边不存在。所以"是不是死配置"要按源码树分别判，不能一刀切。

### 3.2 已落实（只删"启动时一定报错的行"，生效值零变化）

| # | 改动 | 文件 | 依据 |
|---|---|---|---|
| S2 | 删 `net.netfilter.nf_conntrack_helper = 1` | `1-netfilter.conf` | 6.12 `nf_conntrack_standalone.c` 的 49 个 procname 里没有它；ImmortalWrt 25.12 的 878 个内核补丁和 LiBwrt 的 624 个都没有添加它。`nf_conntrack_helper` 自 5.x 起是模块参数（`/sys/module/nf_conntrack/parameters/`），不是 sysctl。四台设备上都是死配置 |
| S3 | 删 `net.ipv4.neigh.default.unres_qlen = 10000` | `0-v4.conf` | 6.12 `neighbour.c:3738-3755` 的 `neigh_parms` 表只有 `unres_qlen_bytes`（字节），没有按包数的 `unres_qlen`；两边补丁都没动这块 |
| S4 | 删重复的 `net.core.netdev_max_backlog = 9000`（保留后面的 32768） | `0-base.conf` | 同文件写两次，sysctl 后写覆盖先写，生效值一直是 32768 |

### 3.3 待定夺（有取舍，或按设备不同）

| # | 项 | 现状 | 收益 / 风险 | 建议 |
|---|---|---|---|---|
| S1 | **`net.netfilter.nf_conntrack_tcp_no_window_check = 1`** | 四台共用一个 `0-base.conf`，但这个 sysctl **只有 NN6000 有**：它来自 LiBwrt 的 QCA NSS ECM 补丁 `qualcommax/patches-6.12/0600-1-qca-nss-ecm-support-CORE.patch:912`；ImmortalWrt 源（R68S / NSY / SystemReady）的 6.12 内核和全部补丁里都没有 | 在三台 ImmortalWrt 设备上启动报错跳过（纯噪音）；在 NN6000 上有效（关掉 TCP 窗口检查，配合 NSS 加速） | **本轮没删**（删了会改 NN6000 行为）。要彻底干净，把这一行从共用的 `0-base.conf` 挪到 `NN6000/diy-part2.sh` 单独写入 |
| S5 | **`net.ipv4.tcp_congestion_control = bbr`** | 四个 `.config` 都是 `# CONFIG_PACKAGE_kmod-tcp-bbr is not set`；6.12 内核 `# CONFIG_TCP_CONG_BBR is not set`、`CONFIG_TCP_CONG_CUBIC=y`。**这行启动时报错，实际一直是 cubic** | 两个选法：(a) 四个 `.config` 加 `CONFIG_PACKAGE_kmod-tcp-bbr=y`，BBR 真正生效（多一个 kmod，`netsupport.mk` 会同时装 `/etc/sysctl.d/12-tcp-bbr.conf`）；(b) 删掉这行，承认用 cubic | 想要 BBR 就选 (a)；这是改包集合，留给你定 |
| S6 | `net.bridge.bridge-nf-call-{iptables,ip6tables,arptables} = 0` | NN6000 / R68S / NSY **没装 `kmod-br-netfilter`**，这三行在这三台本来就是死配置；只有 SystemReady 装了 `kmod-br-netfilter` + `kmod-nft-bridge`，关掉后 LAN 内互访不过 nftables 防火墙（OpenWrt 默认是开的） | 性能收益有限；安全上少一层 | 三台死配置可以删；SystemReady 看你是否需要 LAN 隔离 |
| S7 | `net.ipv4.tcp_syn_retries = 1` / `tcp_synack_retries = 1` | 内核最小值就是 1（合法），但 1 意味着首个 SYN 约 3 秒无应答就放弃 | 对高延迟/丢包链路（跨境、代理场景）连接容易失败 | 建议 2-3 |
| S8 | `net.ipv4.tcp_timestamps = 0` | BBR 和 RACK 依赖时间戳做 RTT 估计；关掉后 BBR 仍能跑但精度下降 | 关掉主要是指纹/隐私考虑 | 如果选了 S5(a) 开 BBR，建议同时把 timestamps 开回 1 |
| S9 | `net.ipv4.tcp_low_latency = 1`、`tcp_fack = 1`、`tcp_early_retrans = 3`、`tcp_ecn_fallback = 1`、`tcp_frto = 0` | procname 在 6.12 都存在，不报错；但 `tcp_low_latency` 在 TCP 代码里零引用（残留开关），`tcp_fack` 已被 SACK/RACK 吸收，`tcp_early_retrans` 4.8+ 已被 RACK 取代 | 写了没用，纯噪音 | 可以删，不急 |
| S10 | `net.core.rmem_default/wmem_default = 64 MB`、`rmem_max/wmem_max = 100 MB`、`tcp_rmem/tcp_wmem` 上限 64 MB | 对 1 GB 内存的 NN6000 偏大；默认缓冲 64 MB 意味着每个 socket 初始就占这么多？不是——`*_default` 只是上限内的初始配额，真实占用按需增长 | 大并发下内存压力 | 看设备内存，1 GB 设备可考虑减半 |
| S11 | `net.netfilter.nf_conntrack_max = 327680`、`buckets = 81920` | 每条 conntrack 约 300 字节，满表约 100 MB；`buckets` 在 6.12 是 per-netns 可写的（`nf_conntrack_standalone.c:630` 指向 `nf_conntrack_htable_size_user`） | 1 GB 设备偏大 | 4 GB 设备没问题；1 GB 设备可降到 65536 |
| S12 | `net.ipv4.conf.all.route_localnet = 1` | 允许 127.0.0.0/8 的包被路由进系统 | 这是透明代理（redirect 到本地端口）需要的 | 用 passwall 透明代理就留着 |
| S13 | `vm.overcommit_memory = 1`（永远不拒绝分配）、`vm.swappiness = 1` | 无 swap 的路由器上 swappiness 无意义；overcommit=1 在内存紧张时更容易 OOM 而不是 malloc 失败 | 影响小 | 可留 |
| S14 | NSY 的 `rc.local` 把 `netdev_budget` 改成 10000，而 `0-base.conf` 设 600 | 同一固件两处矛盾，启动后 rc.local 覆盖 sysctl | 属于 NSY 板级既有设计 | 确认是有意为之就留；否则统一 |
| S15 | DIY2 的 `wget` 没有失败检查（`diy-part2.sh` 没 `set -e`） | 任一 `wget` 失败时固件会缺对应文件但构建继续 | 本次没改（超出授权） | 建议加 `|| exit $?` |

### 3.4 已核对无误、保留

- `net.core.dev_weight`、`netdev_budget`、`netdev_budget_usecs`、`somaxconn`、`optmem_max`、`bpf_jit_enable`、`bpf_jit_kallsyms`：6.12 `net_core_table[]` 都有。
- `net.ipv4.conf.{all,default}.{rp_filter,route_localnet,accept_redirects,secure_redirects,send_redirects,arp_ignore}`：`devinet.c` 宏生成，存在。
- `net.ipv4.neigh.default.{base_reachable_time_ms,retrans_time_ms,mcast_solicit,gc_thresh1-3}`：`neighbour.c` 存在。
- `fs.file-max`：`fs/file_table.c:115` 存在。
- `net.nf_conntrack_max` 与 `net.netfilter.nf_conntrack_max`：**两个都存在**（6.12 同时注册 init_net 的 `net/` 和 per-netns 的 `net/netfilter/`），保留两者。
